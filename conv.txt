How AWS Knows GitHub is Assuming the Role (OIDC)

  This uses OpenID Connect (OIDC) federation. Here's the flow:

  1. GitHub generates a JWT token

  When a workflow runs, GitHub's OIDC provider issues a signed JWT containing claims like:
  {
    "iss": "https://token.actions.githubusercontent.com",
    "sub": "repo:your-org/your-repo:ref:refs/heads/main",
    "aud": "sts.amazonaws.com",
    ...
  }

  2. AWS has a trusted Identity Provider configured

  You (or CloudFormation) previously registered GitHub's OIDC provider in AWS IAM:
  - Provider URL: https://token.actions.githubusercontent.com
  - Audience: sts.amazonaws.com

  AWS fetches GitHub's public keys from that URL to verify the JWT signature.

  3. The IAM Role has a Trust Policy

  The role (AWS_ROLE_ARN) has a trust policy like:
  {
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::ACCOUNT:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringLike": {
        "token.actions.githubusercontent.com:sub": "repo:your-org/your-repo:*"
      }
    }
  }

  4. The aws-actions/configure-aws-credentials action calls sts:AssumeRoleWithWebIdentity

  It sends the JWT to AWS STS. AWS:
  1. Verifies the JWT signature using GitHub's public keys
  2. Checks the sub/aud claims match the trust policy conditions
  3. Issues temporary credentials if everything checks out

  Key Point

  No long-lived secrets (access keys) are needed. The AWS_ROLE_ARN secret only contains the role ARN (not a credential) — the actual authentication is the
  signed JWT that GitHub generates per-run.

❯ what if some one pretend they are github

⏺ What Prevents Someone from Impersonating GitHub?

  The JWT is Cryptographically Signed

  GitHub signs the JWT with a private key that only GitHub possesses. AWS verifies the signature using GitHub's public keys fetched from:

  https://token.actions.githubusercontent.com/.well-known/jwks

  An attacker can't forge a valid JWT without GitHub's private key — so a fake token would fail signature verification.

  ---
  Even with a Valid GitHub Token — the Trust Policy's sub Condition Blocks Other Repos

  "Condition": {
    "StringLike": {
      "token.actions.githubusercontent.com:sub": "repo:your-org/your-repo:*"
    }
  }

  GitHub's JWT sub claim is set server-side and encodes exactly which repo triggered the workflow. A workflow in attacker-org/evil-repo would get a token
  with:
  "sub": "repo:attacker-org/evil-repo:ref:refs/heads/main"
  ...which doesn't match your condition, so AWS rejects the AssumeRole call.

  ---
  Summary of the trust chain

  ┌───────────────────────────────────────────────┬────────────────────────────────────────────────────────────────┐
  │                    Attack                     │                          Why it fails                          │
  ├───────────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
  │ Forge a GitHub JWT                            │ Can't — no access to GitHub's private signing key              │
  ├───────────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
  │ Use a real GitHub token from a different repo │ sub claim won't match the trust policy condition               │
  ├───────────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
  │ Replay an old token                           │ JWTs have short expiry (exp claim), AWS rejects expired tokens │
  ├───────────────────────────────────────────────┼────────────────────────────────────────────────────────────────┤
  │ MITM between GitHub and AWS STS               │ HTTPS + AWS verifies GitHub's OIDC endpoint via TLS            │
  └───────────────────────────────────────────────┴────────────────────────────────────────────────────────────────┘

  The security guarantee is: only a workflow running inside your-org/your-repo on GitHub's infrastructure can produce a JWT that passes both the signature
  check and the trust policy condition.

⏺ No — They Are Learned Weights, Not Created Per Token

  The embedding tables are fixed matrices stored in the model. They don't get created — they get looked up.

  ---
  token_embed (50257 × 256)

  - A table with 50257 rows (one per vocabulary token) and 256 columns (embedding dimension)
  - When token 42 arrives → just grab row 42 from the table
  - The table itself never changes during inference (only during training)

  token_id = 42
  vector = token_embed[42]  # just an index lookup, O(1)

  ---
  pos_embed (100 × 256)

  - A table with 100 rows (one per position, so max sequence length = 100)
  - Token at position 0 → grab row 0, token at position 1 → grab row 1, etc.

  position = 3
  vector = pos_embed[3]  # lookup by position

  ---
  What actually happens per token

  input:  token_id=42, position=3

  output: token_embed[42]   ← 256-dim vector (what is this token?)
        + pos_embed[3]      ← 256-dim vector (where is this token?)
        = 256-dim vector    ← this is what flows into the transformer

  ---
  Summary

  ┌───────────────────┬─────────────┬──────────────────────────┐
  │                   │ Created at? │        Per token?        │
  ├───────────────────┼─────────────┼──────────────────────────┤

  ├───────────────────┼─────────────┼──────────────────────────┤
  │ pos_embed table   │ Training    │ No — looked up           │
  ├───────────────────┼─────────────┼──────────────────────────┤
  │ The sum vector    │ Inference   │ Yes — computed per token │
  └───────────────────┴─────────────┴──────────────────────────┘

  The tables are weights learned during training. At inference, you're just doing array indexing into them.

⏺ Full Transformer Steps (from embedding → output)

  Step 1: Embedding (what you just saw)

  token_embed[42] + pos_embed[3] = x  (256-dim vector)
  Do this for every token in the sequence. Say you have 5 tokens:
  x = [x0, x1, x2, x3, x4]   shape: (5 × 256)

  ---
  Step 2: QKV Projection (inside Attention)

  Three learned weight matrices project x into Q, K, V:
  Q = x @ W_q    (5 × 256) @ (256 × 64) = (5 × 64)   "what am I looking for?"
  K = x @ W_k    (5 × 256) @ (256 × 64) = (5 × 64)   "what do I contain?"
  V = x @ W_v    (5 × 256) @ (256 × 64) = (5 × 64)   "what do I give if chosen?"

  ---
  Step 3: Attention Scores

  scores = Q @ K^T / sqrt(64)        shape: (5 × 5)
  Each row = how much token i attends to every other token.

  ---
  Step 4: Softmax → weights sum to 1

  weights = softmax(scores)          shape: (5 × 5)

  ---
  Step 5: Weighted sum of V

  attn_out = weights @ V             shape: (5 × 64)
  Each token now carries information from other tokens it attended to.

  ---
  Step 6: Project back + Residual

  attn_out = attn_out @ W_o          (5 × 64) → (5 × 256)
  x = x + attn_out                  residual connection (add original x back)
  x = LayerNorm(x)

  ---
  Step 7: Feed Forward Network (FFN)

  x = x + FFN(x)                    expand → activate → shrink
  x = LayerNorm(x)
  Typically: 256 → 1024 → 256 with ReLU/GELU in between.

  ---
  Step 8: Repeat (N layers)

  Steps 2–7 repeat for each transformer block (e.g. 6 or 12 times).

  ---
  Step 9: Final output — predict next token

  logits = x @ token_embed^T         (5 × 256) @ (256 × 50257) = (5 × 50257)
  probs  = softmax(logits[-1])       look at LAST token's row only
  next_token = argmax(probs)         pick most likely next token

  ---
  Full picture

  tokens
    ↓
  [embed + pos]
    ↓
  ┌─────────────────┐
  │  Q,K,V project  │
  │  Attention      │  ← tokens talk to each other
  │  + Residual     │
  │  LayerNorm      │
  │  FFN            │  ← each token thinks independently
  │  + Residual     │
  │  LayerNorm      │
  └─────────────────┘  ← repeat N times
    ↓
  logits → softmax → next token

  The key insight: Q/K decide who attends to whom, V decides what information is passed.

❯ is token embed a embeddiung vocabulary

⏺ Yes, exactly.

  token_embed (50257 × 256) is the embedding vocabulary (lookup table).

  vocab size = 50257  (GPT-2's tokenizer has 50257 possible tokens)
  embed dim  = 256    (each token maps to a 256-dim vector)

  Every possible token in the vocabulary has one row in this table:

  token "hello" → id 31373 → token_embed[31373] → [0.2, -0.5, 0.1, ...]  (256 numbers)
  token "world" → id 995   → token_embed[995]   → [0.8,  0.3, 0.9, ...]  (256 numbers)
  token "the"   → id 262   → token_embed[262]   → [-0.1, 0.7, 0.2, ...]  (256 numbers)

  These 256 numbers encode meaning — tokens with similar meanings end up with similar vectors (learned during training).

  ---
  So the full picture:

  text  →  tokenizer  →  token IDs  →  token_embed lookup  →  vectors
  "hello world"  →  [31373, 995]  →  2 rows from the table  →  (2 × 256)

  token_embed is literally just a big matrix where row i = the learned vector for token i.

❯ why every step looks having diff functionality

⏺ Because each step solves a different problem that the others can't.

  ---
  The problems they each solve:

  ┌──────────────────┬──────────────────────────────────────────────────────────────────────────────┐
  │       Step       │                              Problem it solves                               │
  ├──────────────────┼──────────────────────────────────────────────────────────────────────────────┤
  │ Embedding        │ Convert token IDs (integers) into vectors the math can work with             │
  ├──────────────────┼──────────────────────────────────────────────────────────────────────────────┤
  │ Q/K (Attention)  │ Let tokens look at each other — understand context and relationships         │
  ├──────────────────┼──────────────────────────────────────────────────────────────────────────────┤
  │ V (Attention)    │ Decide what information to actually pass once you know who to attend to      │
  ├──────────────────┼──────────────────────────────────────────────────────────────────────────────┤
  │ Residual (+x)    │ Don't forget the original signal — prevent information loss in deep networks │
  ├──────────────────┼──────────────────────────────────────────────────────────────────────────────┤
  │ LayerNorm        │ Keep numbers stable — prevents values from exploding or vanishing            │
  ├──────────────────┼──────────────────────────────────────────────────────────────────────────────┤
  │ FFN              │ Let each token think independently — process the gathered context deeper     │
  ├──────────────────┼──────────────────────────────────────────────────────────────────────────────┤
  │ Final projection │ Convert back to vocabulary space to predict the next token                   │
  └──────────────────┴──────────────────────────────────────────────────────────────────────────────┘

  ---
  Simple analogy — reading a sentence to answer a question:

  Embedding     →  you read the words (convert symbols to meaning)
  Attention     →  you look back at earlier words for context
                   ("it" → who does "it" refer to?)
  FFN           →  you reason about what you gathered
  Residual      →  you don't forget what you already knew
  LayerNorm     →  you stay calm, don't over/under-react
  Final project →  you produce an answer

  ---
  Core idea:

  No single step can do everything. Attention is good at relating tokens but bad at deep reasoning. FFN is good at reasoning but blind to other tokens. They
  are designed to be complementary — each fills the gap the others leave.

❯ so is tis a permanent step? or defined per layer

⏺ Both — some are permanent (happen once), some repeat per layer.

  ---
  Happens ONCE:

  tokens → Embedding + Positional   ← just at the start

  ---
  Repeats EVERY layer:

  ┌─────────────────────┐
  │  Q, K, V projection │
  │  Attention          │
  │  + Residual         │
  │  LayerNorm          │
  │  FFN                │
  │  + Residual         │
  │  LayerNorm          │
  └─────────────────────┘  ← this entire block repeats N times

  Each layer has its own separate weights for Q, K, V, FFN. They are not shared.

  ---
  Why repeat?

  Each layer learns something different and deeper:

  Layer 1  →  simple patterns   (grammar, punctuation)
  Layer 2  →  syntax            (subject, verb, object)
  Layer 3  →  semantics         (meaning, relationships)
  ...
  Layer N  →  high-level reasoning, facts, context

  Early layers = low level. Deep layers = high level. This is the same reason CNNs stack convolution layers — complexity builds up gradually.

  ---
  Happens ONCE at the end:

  last layer output → Final projection → logits → next token

  ---
  Full picture:

  [Embedding]          ← once
      ↓
  [Layer 1]            ← own weights
  [Layer 2]            ← own weights
  [Layer 3]            ← own weights
     ...
  [Layer N]            ← own weights
      ↓
  [Final projection]   ← once

  GPT-2 small = 12 layers. GPT-3 = 96 layers.

  │ Block  │ A module (a group of layers with weights)             │

⏺ Yes, exactly — they're two different things and people often conflate them.

  MLflow = a specific open-source product (from Databricks). When I said "no MLflow," I literally meant nothing in this repo does import mlflow, runs an

  1. Source/data/model versioning
  2. Reproducible training (CI)
  3. Experiment tracking
  4. Model registry + approval workflow
  5. Automated deployment (CD)
  6. Monitoring (drift, performance, cost)
  7. Retraining triggers
  8. Governance (lineage, model cards, bias/explainability)
  9. Observability & alerting
  10. Tests + rollback

  So for this repo:
  - MLflow framework: 0% — it's just not used.
